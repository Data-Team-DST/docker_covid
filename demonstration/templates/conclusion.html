🧭 Conclusion et perspectives

Ce projet industrialise un modèle issu d'une phase Data Science exploratoire antérieure (voir Contexte DS) — la conclusion ci-dessous porte sur l'industrialisation MLOps elle-même (Phases 1→4), pas sur la phase exploratoire d'origine.

1. Ce qui a été industrialisé

  • ✅ Environnement reproductible, API FastAPI sécurisée (clé X-API-Key, rate limiting, validation stricte des uploads)
  • ✅ Découpage en microservices HTTP-only (backend, segmentation-service, data-service, dvc-service, log-service) — voir Architecture
  • ✅ Versionnage des données (DVC, remote MinIO) et des modèles (MLflow tracking + Model Registry)
  • ✅ CI/CD complet : lint → tests → SonarCloud → build/push GHCR (3 services) → smoke-test de déploiement
  • ✅ Docker Compose production-ready : healthchecks et limites mémoire sur tous les services, 0 secret en dur
  • ✅ Monitoring : dashboard Grafana (latence p50/p95, taux d'erreurs, distribution des prédictions par classe) + alertes Prometheus, rapport de dérive Evidently générable à la demande — voir Monitoring

2. Limites et incidents rencontrés en cours de route

Assumés plutôt que masqués — une industrialisation MLOps se juge aussi à la façon dont elle détecte et corrige ses propres angles morts :

  • Train/serving skew — l'ordre des classes dans le backend ne correspondait pas à celui figé par le pipeline d'entraînement (dvc.lock). Détecté par test batch réel (matrice de confusion), pas par un exemple isolé. Corrigé le 2026-08-28 : accuracy 35 % → 78 % sur un lot de test.
  • Instabilité mémoire de segmentation-service sous appels séquentiels — stopgap appliqué (limite mémoire relevée), cause racine (gestion mémoire TensorFlow entre appels predict()) non résolue.
  • CI "Deploy smoke-test" intermittente — root-causée (retry MLflow trop lent dans la fenêtre de test) et corrigée.
  • Pipeline DVC désynchronisé localement (dvc status signale des écarts entre params.yaml/données sur disque et le dernier dvc.lock figé) — connu, pas encore traité.
